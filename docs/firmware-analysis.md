# 公式ファーム `.hfb` 解析結果（2026-06-13）

対象: `HHKB820_FW_JP_A248.hfb`（PFU 公式提供・HYBRID Type-S 日本語配列 PD-KB820B 用・最新版 A248）

> この `.hfb` は **PFU 公式が配布する正規ファーム**。これが手に入ったことで、
> 危険な `0xD0` ダンプ（更新モード移行を誘発する）を実行する必要が無くなった。
> 48バイトだけ取れたダンプ `firmware_jis.bin` は、この `.hfb` のヘッダ4バイトを
> 除いた本体先頭と**バイト単位で一致**しており、`0xD0` が本物を吐いていたことの裏付けになった。

## ファイル構造

```
offset 0      [4B header]   03 4a fb 67   ← 非標準の整合値（後述）
offset 4      [flash image] e8 24 00 20 ... ← ベクタテーブル先頭（= 0x08010000 にロードされる）
...           [code/data]
末尾付近      [0xFF padding]
末尾         [footer]       "AHJX01" 0a 02 04 08 ff...  ← モデルID + 版数らしき4バイト
```

- ファイルサイズ: 282,672 bytes（本体 282,668 bytes）
- 0xFF 比率 12.0% / 0x00 比率 7.7%（= padding と未使用領域。暗号化なら現れない）

## アーキテクチャ：STM32（ARM Cortex-M, Thumb2）確定

ベクタテーブルが Cortex-M の教科書どおり：

| 項目 | 値 | 意味 |
|------|-----|------|
| 初期スタックポインタ | `0x200024e8` | RAM ベース `0x20000000`（STM32 系） |
| リセットベクタ | `0x080100d5` | Flash、Thumb ビット付き → 実体 `0x080100d4` |
| **アプリ Flash ベース** | **`0x08010000`** | **Ghidra のロードアドレスはこれ** |
| ブートローダ領域 | `0x08000000`〜`0x0800FFFF`(64KB) | **触らない**（`UPDATEBOOT_*` 禁止の根拠） |

第1〜第3ベクタ: `0x08015401`, `0x080144c9` … 既定ハンドラ `0x080100e7` が連続（典型パターン）。

## 暗号化されていない（重要）

- 本体エントロピー **6.59 bits/byte**（チャンク 4.8〜7.0）
- 暗号化されていれば一様に ~8.0 になる → **平文の ARM コードと確定**
- 「暗号化で詰み」シナリオは消えた

## 埋め込み文字列

- `PFU Limited`
- `HHKB-Hybrid`（USB プロダクト文字列）
- `BT(F...`（Bluetooth/Fn 関連の処理ラベルか。要調査）
- `AHJX01`（末尾フッタのモデルID）

## 4バイトヘッダ `03 4a fb 67` の整合スキーム

標準 CRC では一致しなかった（総当たり検証済み）：
- CRC16: CCITT-FALSE / XMODEM / KERMIT / MODBUS / ARC / MAXIM / USB / CDMA2000 / DNP → 全て不一致
- CRC32: zlib / 反転 → 不一致
- 単純 sum16/sum32 → 不一致
- 対象範囲: body 全体 / 末尾 0xFF 除去 いずれも不一致

→ **独自の整合計算（シード違い・対象範囲違い・独自多項式のいずれか）**。
ファーム本体に FIRMUP 受信＆検証ルーチンが含まれるはずなので、
**Ghidra で検証ルーチンを読めば算出方法が判明する**見込み。
